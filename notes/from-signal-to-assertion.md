# 从「信号」到「断言」：怎么让一个失败真的失败

这篇是通用方法论笔记，起因是 vim/vim#21255 里维护者 chrisbra 重写了我们的测试。
具体到 Vim 泄漏测试的三种模式见 [vim-leak-test-patterns.md](vim-leak-test-patterns.md)。

---

## 一、断言要断的，是「我们感兴趣的、可观测的异常」

这是一个**抽象槽位**，填什么随被测对象而变。填进去的是什么，是整件事里
杠杆最大的一步——比后面所有工程手段加起来都重要。

### 没有「缺陷本体」这回事

很容易以为存在一个特权的"缺陷本身"，ASan 报告是它，退出码只是它的影子。经不起推敲：

`string_reduce` 的缺陷是「`funccall_T` 滞留在 `current_funccal` 链上」。
ASan 那份 stack-use-after-return 报告**并不是这个东西本身**——它是
「对一个已中毒的 fake-stack 槽位发生了访问」，同样是下游后果。
`test_refcount(p1) == 2` 也是后果。

**两个都是被我们挑中的观测，没有谁更本体。**

### 于是真问题只剩一个：代码能不能直接读到它

| 选定的异常 | 代码能直接读吗 | 要补什么 |
|---|---|---|
| `test_refcount(p1)` | 能 | 什么都不用 |
| ASan 报告 | 不能，只在 stderr 上 | 变致命 + 子进程 + 压噪声 + 守卫 + 恢复现场 |

读不到就得搭一条转换链。chrisbra 那条是六步：

```
缺陷 → ASan 检测到 → 报告打到 stderr → abort_on_error 使其致命
     → 子进程 SIGABRT → 退出码 134 → 断言读到
```

断言站在链的末端。链一长，就得交两笔税——注意这是**距离**的税：

- **压噪声**：退出码非 0 有太多别的来源（语法错、启动失败、文件找不到）。
  `qall!` 保证正常路径必然退 0，`silent!` 挡住 E684 走上别的退出路径——
  把其他一切退出路径压平，让 134 只可能来自 ASan。
  距离越远，中间环节越多，别的原因也越容易让末端取到异常值。
- **防真空**：观测手段本身可能缺席，`CheckAsan` 守的就是这个（第四节）。

反过来，`test_refcount` 链长为 1，这两笔税一分不交：没有别的东西会让引用计数
变成 2，引用计数在任何构建里都存在。

> **代理链有多长，这个测试就需要多少附属设施。**

### 最要紧的一步在最前面：挑哪个异常

`f_setmatches` 是最好的例子。候选异常有两个：

- **ASan/LSan 报告** → 无效。泄漏的 list 挂在全局 `first_list` 链上，
  LSan 认为它可达，修复前后两棵树都退出 0。距离无穷远，搭多少链子都到不了。
- **`posN` 的引用计数** → 一行断言搞定。

把问题定义成「怎么让 ASan 报告变得可断言」，这里是死路；
定义成「**该挑哪个异常**」，出口立刻出现。

所以判断顺序是：

> **先列出这个缺陷会造成哪些异常现象，挑距离最近的那个；
> 挑完仍然够不着，才去搭转换链，并按距离准备设防。**

插桩不是 fallback，它只是候选之一——而且经常不是最好的那个。

### 顺带：裁决权

链搭好之后，还有一件跟着搬家的事。改造前 ASan 报告只对**外部观察者**可见
（CI 的 grep），裁决在 CI 脚本里；改造后它对**测试进程**可见，裁决在测试里。
这是测试变得自洽的原因——本地 `make test_vim9_builtin` 就能跑出红灯，
不必等 CI 去捞日志。

（还有一件事**不在这条链上**，因而无论怎么表述都容易漏掉——见第四节。）

## 二、把 chrisbra 那段代码拆开

```vim
def Test_string_reduce_error_funccal()
  CheckAsan                                              " ① 前提守卫

  var save = $ASAN_OPTIONS
  defer setenv('ASAN_OPTIONS', save)                     " ④ 恢复现场
  $ASAN_OPTIONS = 'detect_stack_use_after_return=1:abort_on_error=1:' .. save   " ② 升级信号

  var lines =<< trim END
      vim9script
      silent! echo reduce("abc", (acc, c) => [][0])
      qall!
  END
  writefile(lines, 'Xreducefc.vim', 'D')
  g:RunVim([], [], '-u NONE -S Xreducefc.vim')           " ③ 隔离
  assert_equal(0, v:shell_error)                         " ⑤ 断言
enddef
```

五个动作，每一个都对应一个可以搬去任何项目的通用问题：

### ① 前提守卫 —— 「这个测试的观测手段真的在场吗？」

`CheckAsan` 检查 `:version` 输出里有没有 `-fsanitize=address`，没有就 **skip 掉，不是通过**。

没有这一行会怎样？在非 ASan 构建上，缺陷仍然存在，进程也仍然退出 0，
于是 `assert_equal(0, v:shell_error)` **通过了**。测试变成了装饰品，而且是最坏的那种：
它给你一个绿灯，让你以为这个 bug 被守住了。

这就是**真空通过（vacuous pass）**，见第四节。

### ② 升级信号 —— 「默认行为是不是'报告完继续跑'？」

绝大多数运行时诊断的默认行为是**不打断执行**：sanitizer 打印报告、编译器打印警告、
Python 打印 DeprecationWarning、Node 打印 UnhandledPromiseRejection。
它们设计成这样是为了不打扰生产环境——但测试环境的诉求恰好相反。

所以第一步永远是去找那个"把警告变成致命错误"的开关。

### ③ 隔离 —— 「致命信号怎么可能被自己捕获？」

一旦②生效，出错就是 SIGABRT。你没法在被自己 abort 掉的进程里执行 assert。
所以必须开子进程：`RunVim` 跑一个独立的 Vim，父进程活着，
子进程的死法变成 `v:shell_error` 这个普通变量。

**进程边界在这里不是负担，是转换器**：它把"不可捕获的事件"翻译成"可读的整数"。

### ④ 恢复现场 —— 「我改的是全局状态吗？」

`$ASAN_OPTIONS` 是环境变量，改了会影响同一个 runner 里后面所有测试。
`defer` 保证无论测试怎么结束都还原。凡是①②里动过全局开关的，都欠这一步。

### ⑤ 断言 —— 「失败在哪里被报出来？」

`assert_equal(0, v:shell_error)`。到这一步测试才**自洽**：
本地 `make test_vim9_builtin` 就能跑出红灯，不需要 CI，不需要人去看日志。

## 三、通用模板

```
先于写测试:
    列出这个缺陷会造成的异常现象         # ← 杠杆最大的一步
    挑距离最近的那个                     # 够得着就直接断言，收工

测试（挑完仍然够不着时）:
    如果 (观测手段不在场):  跳过        # ← 不是通过
    保存全局状态; 结束时恢复
    打开「诊断即致命」开关
    在隔离边界内执行触发路径
    断言(边界带回的那个值 == 期望)
```

套到别的领域：

| 领域 | 旁路信号 | ②升级信号的开关 | ③边界 | ⑤断言对象 |
|---|---|---|---|---|
| ASan/UBSan/TSan | stderr 报告 | `halt_on_error=1` `abort_on_error=1` `exitcode=` | 子进程 | 退出码 |
| LeakSanitizer | 退出时报告 | 默认已是非 0（ASan 内置时 1，独立 LSan 是 23）| 子进程 | 退出码 |
| 编译器警告 | 编译日志 | `-Werror` / `#pragma`（局部） | 编译命令 | 编译是否成功 |
| Python 警告 | stderr | `-W error` / pytest `filterwarnings = error` | 同进程即可 | 是否抛异常 |
| Node 未处理 Promise | 警告 | `--unhandled-rejections=throw`（新版已是默认）| 子进程 | 退出码 |
| Go goroutine 泄漏 | 无 | `goleak.VerifyTestMain` | 同进程 | goleak 的断言 |
| 日志里的 ERROR | 日志文件 | 无——改用捕获 handler | 同进程 | 捕获到的记录条数 |
| SQL N+1 | 慢 | 无——改用 query 计数器 | 同进程 | 计数 == 预期 |
| 文件描述符泄漏 | 无 | 无——前后各数一次 | 同进程 | 前后相等 |

后面几行值得注意：**并不是所有信号都存在"变致命"的开关**。
没有开关的时候，②③就退化成"自己造一个进程内的可观测量"（计数器、快照对比），
这时候反而不需要子进程了。这就引出第五节。

## 四、最容易忘的那条：真空通过

这一条**不在那条转换链上**。链管的是「异常存在时怎么把它送到断言手里」；
这一条管的是「观测手段根本不在场时会怎样」——而这正是它容易被漏掉的原因。

**缺席不等于成功。** 这是我这一轮里踩了两次的同一个坑：

1. `results/infer-arg-models/verify_patch.sh`：未打补丁的 Infer 遇到新选项会
   报 unknown option 直接退出、**不生成报告文件**。而我有一项检查是
   "期望报告数为 0"——于是它以完全错误的理由通过了。12 项里有 6 项这样通过。
   修法是在前置检查失败时 `exit 1`，不让后面的检查有机会假装成功。

2. Vim 测试：**失败的测试根本不写 `.res` 文件**。我用 `wc -c < test_match.res`
   判断，文件不存在被 shell 读成 0 字节 = 没有失败输出 = 通过。
   于是我向你报告"两棵树都通过"，而未打补丁那棵其实正按设计失败。

`CheckAsan` 防的是**第三种同款**：观测手段缺席，被读成"没有问题"。

> 写完断言，永远再问一遍：**如果我要观测的东西根本没运行，这个测试会是什么颜色？**
> 答案必须是"跳过"或"红"，绝不能是"绿"。

推论：**一个测试在修复前必须真的红过。** chrisbra 直接沿用了我们验证过的那段触发脚本
（连 `qall!` 写在脚本里这个细节都原样保留），因为那段是唯一被证实能在未修复的树上
把它炸出来的输入。断言机制再漂亮，触发路径不对就全是空转。

## 五、把第一节那句话坐实：挑对异常，整条链都不用搭

第二、三节那套（改环境变量 + 开子进程 + 读退出码）**从来不是默认选项**，
它是「挑中的异常代码读不到」之后的补救。挑对了，一件都不用。

我们 `f_setmatches` 那个补丁就是例子。它泄漏的 list 挂在全局 `first_list` 链上，
LeakSanitizer 根本看不见，两棵树都退出 0——模式 A 完全失效。
但被扣住不放的 `posN` 是**脚本里的对象**，Vim 的 `test_refcount()` 直接暴露它的引用计数：

```vim
let p1 = [1, 1, 1]
call assert_equal(1, test_refcount(p1))
call setmatches([#{group: 'Search', priority: 10, id: 4, pos1: p1, pos2: p2}])
call clearmatches()
call assert_equal(1, test_refcount(p1))   " 未修复：2
```

优点是压倒性的：不需要 ASan 构建、不需要子进程、不需要动全局状态、
没有前提守卫要写（所以也没有真空通过的风险）、在所有 CI 上都跑。

注意这里的关键不是"运气好，正好有个 refcount"。是**问题定义方式不同**：
问「怎么让 ASan 报告变得可断言」，`f_setmatches` 无解（LSan 看不见它）；
问「这个缺陷还造成了什么别的可观测异常」，一行就写完了。

**判断顺序：**

1. 列出候选异常——引用计数、句柄数、缓存大小、队列长度、query 条数、
   sanitizer 报告、日志、退出码……
2. 挑代码能直接读到的那个 → 直接断言，收工。
3. 全都够不着 → 才搭转换链，并按链长准备设防（压噪声 + 守卫 + 恢复现场）。

---

## 六、一句话

> 测试的价值不在于"跑过了那段代码"，而在于**它自己有能力说不**。
>
> 先挑准那个「我们感兴趣的、可观测的异常」——这一步的杠杆比后面所有工程手段都大；
> 代码够不着它，才升级信号、开子进程、压噪声，把它送到断言手里；
> 最后回头检查：观测手段缺席时，它是跳过还是撒谎。
